# 🔄 No_ordering 재해석 라운드 (jiyun 브랜치) — 팀원용 요약

> **이번에 뭘 바꿨고 왜 점수가 올랐는지**를, 이 프로젝트를 처음 보는 사람도 이해할 수 있게 차근차근 정리했습니다.
> 한 줄 요약: **`No_ordering`이라는 걸 우리가 처음부터 오해하고 있었고, 그걸 바로잡았더니 test 점수(LB)가 0.88132 → 0.90052로 올랐습니다.**

---

## 0. 먼저 알아야 할 것 — "모델이 실제로 뭘 출력하나?"

이 뒷부분(mid/plain 스타일)을 이해하려면, 우리 AI가 답을 **어떤 글자로 뱉는지**부터 알아야 합니다.

우리 모델은 이미지 4장을 보고 **텍스트로** 답을 씁니다. 그 답에는 두 가지 표현이 등장합니다.

### `Answer: [2, 3, 1, 4]` 가 무슨 뜻?
**"각 입력 프레임이 시간순으로 몇 번째냐"** 를 순서대로 적은 것입니다.

예를 들어 `Answer: [2, 3, 1, 4]` 는:
- Frame 1 → 시간순 **2**번째
- Frame 2 → 시간순 **3**번째
- Frame 3 → 시간순 **1**번째 (제일 먼저!)
- Frame 4 → 시간순 **4**번째 (제일 나중)

이게 우리가 대회에 **제출하는 최종 정답** 형식입니다.

### `Order: Frame 3 -> Frame 1 -> Frame 2 -> Frame 4` 가 무슨 뜻?
같은 내용을 **시간순으로 나열**한 것입니다. "제일 먼저는 Frame 3, 그다음 Frame 1, …". 위 `Answer`와 똑같은 말을 방향만 바꿔 쓴 거예요. 모델이 생각을 정리하는 용도로 먼저 씁니다.

> 정리: **`Order`는 "시간순 줄 세우기", `Answer`는 "각 프레임의 등수"**. 같은 정답의 두 표현입니다.

이제 이 두 표현이 어떻게 조합되는지가 **"스타일"** 입니다. 뒤에서 자세히 봅니다.

## 1. 무엇을 발견했나 (핵심)

데이터에 `No_ordering`이라는 컬럼이 있습니다. 전체의 15.5%가 `True`이고, 그 샘플들의 정답은 전부 `[1, 2, 3, 4]`입니다.

우리는 이걸 **"순서를 정할 수 없는 문제"**(프레임이 애매해서 정렬 불가능)라고 이해하고 있었습니다. 그런데 **공식 데이터 설명을 다시 읽어보니 뜻이 완전히 달랐습니다:**

> **"No_ordering: True일 경우 이미지는 셔플링되지 않았으며, 정답은 [1, 2, 3, 4]로 고정됩니다."**

즉 `No_ordering=True`는 **"출제자가 이 샘플은 안 섞었다"**는 뜻입니다. 프레임이 애매한 게 아니라, **원래 시간순 그대로인 정상 영상**이에요. 안 섞었으니 답이 `[1,2,3,4]`(= Frame 1이 1번째, Frame 2가 2번째… 이미 순서대로)인 거고요.

**비유하면**: 카드 4장을 섞는 게임인데, 딜러가 15.5%의 판은 **일부러 안 섞고** 그대로 준 겁니다. "안 섞은 판"이 "맞출 수 없는 판"은 아니죠. 오히려 제일 쉬운 판입니다.

### 증거 (추측 아니라 데이터로 확인함)

| # | 관측 | 옛 해석("정렬 불가")으로 설명되나? |
|---|---|---|
| 1 | no_ordering 샘플 프레임을 직접 열어보니, 캡션 순서와 **완벽히 시간순 일치** | ❌ 정렬 불가면 이럴 수 없음 |
| 2 | **모델이 섞인 no_ordering 프레임의 원래 순서를 59.6% 복원** (em_no_ordering 0.596) — 일반 문제(0.503)보다 오히려 잘 맞힘 | ❌ "정렬 불가"한 걸 정렬한다? 모순 |
| 3 | 검은 프레임·중복 프레임 같은 노이즈가 두 그룹에 **똑같이** 분포 | ❌ no_ordering이 노이즈 덤프였다면 한쪽에 몰려야 함 |

②번이 결정적입니다. **채점할 때 no_ordering 샘플도 똑같이 섞어서 물어보는데**, 모델이 원래 순서를 59.6%나 맞힙니다. 정렬이 불가능하면 이게 불가능하죠. **두 그룹은 그냥 같은 난이도의 같은 문제**였습니다.

## 2. "스타일"이 뭔가 — `mid`(옛날) vs `plain`(새것)

모델한테 답을 **어떤 형식으로 쓰라고 가르치느냐**를 "스타일"이라고 부릅니다. 이번 변경의 핵심이 바로 이 스타일을 `mid`에서 `plain`으로 바꾼 것입니다.

### 🟥 옛날 방식: `mid` 스타일

모델한테 이렇게 답하라고 가르쳤습니다.

**일반 문제(섞인 영상)일 때:**
```
Order: Frame 3 -> Frame 1 -> Frame 2 -> Frame 4
Conclusion: ORDERABLE          ← "이건 순서를 정할 수 있어요"
Answer: [2, 3, 1, 4]
```

**no_ordering(안 섞은 영상)일 때:**
```
Conclusion: UNORDERABLE        ← "이건 순서를 못 정하겠어요"
Answer: [1, 2, 3, 4]
```

가운데에 **`Conclusion:` 줄**이 있는 게 보이죠? 여기서 모델이 "이 문제는 순서를 정할 수 있다(ORDERABLE) / 없다(UNORDERABLE)"를 **선언**하게 시켰습니다. 우리가 no_ordering을 "정렬 불가"로 오해했기 때문에 만든 줄이에요.

### 💥 그런데 이 `mid` 방식이 고장나 있었습니다

문제가 두 개였어요.

**문제 A — 모델이 `UNORDERABLE`을 한 번도 안 씀 (모드 붕괴)**

위 두 예시를 보면, 답이 시작하는 **첫 단어가 다릅니다**:
- 일반 문제 → `Order:` 로 시작
- no_ordering → `Conclusion:` 로 시작

즉 모델은 답의 **맨 첫 글자**에서 이미 "순서 있는 문제냐 없는 문제냐"를 결정해야 합니다. 그런데 학습 데이터의 **84.5%가 `Order:`로 시작**하다 보니, 모델이 그냥 **무조건 `Order:`부터 쓰는 습관**이 들어버렸어요. 한번 `Order:`(순서 나열)를 써버리면 "순서를 못 정하겠다(UNORDERABLE)"고 말할 수가 없죠.

결과: 6,552번 답하는 동안 **`UNORDERABLE`을 단 0번** 출력했습니다. 우리가 가르친 걸 모델이 통째로 무시한 거예요.

**문제 B — 학습 데이터 15.5%에 거짓말을 가르침**

no_ordering 샘플을 학습시킬 때, **프레임은 섞어놓고 정답은 `[1,2,3,4]`로 고정**했습니다. 섞었으면 정답도 바뀌어야 하는데 "섞였는데도 답은 그대로"라고 가르친 겁니다. → 모델한테 "이 영상들은 프레임 보지 말고 그냥 `[1,2,3,4]` 뱉어"를 훈련시킨 셈.

### 🟩 새 방식: `plain` 스타일

`UNORDERABLE`이라는 개념을 **통째로 없앴습니다.** `Conclusion:` 줄을 빼고, **모든 문제를 똑같은 형식**으로 답하게 했어요.

**일반 문제(섞인 영상)일 때:**
```
Order: Frame 3 -> Frame 1 -> Frame 2 -> Frame 4
Answer: [2, 3, 1, 4]
```

**no_ordering(안 섞은 영상)일 때:**
```
Order: Frame 1 -> Frame 2 -> Frame 3 -> Frame 4      ← 이미 순서대로니까 1,2,3,4
Answer: [1, 2, 3, 4]
```

**핵심**: no_ordering도 특별할 게 없습니다. 그냥 **"정답이 [1,2,3,4]인 평범한 순서 문제"**예요. 모델이 `[1,2,3,4]`라고 답하면 그게 자동으로 "이 영상은 이미 순서대로다 = no_ordering"라는 뜻이 됩니다. 별도 선언이 필요 없어요.

### 나란히 비교

| | `mid` (옛날) | `plain` (새것) |
|---|---|---|
| `Conclusion:` 줄 | 있음 (ORDERABLE/UNORDERABLE 선언) | **없음** |
| no_ordering 처리 | "순서 못 정함"이라는 특수 케이스 | 그냥 답이 `[1,2,3,4]`인 일반 문제 |
| 첫 단어 | 문제마다 다름 (`Order:` or `Conclusion:`) | **항상 `Order:`** (분기 없음) |
| 모드 붕괴 | 있음 (UNORDERABLE 0번 출력) | 없음 (애초에 그 개념이 없음) |
| 거짓 라벨 | 있음 (섞고도 [1,2,3,4] 고정) | **없음** (아래 참조) |

## 3. 함께 고친 것 — 진실 라벨 + 사전확률

`plain` 스타일로 바꾸면서 학습 방식도 두 가지 손봤습니다.

### ① 진실 라벨 증강
"증강"이란 **한 문제를 여러 방식으로 섞어서 여러 문제처럼 학습**시키는 기법입니다 (데이터를 뻥튀기). 예전엔 no_ordering을 섞고도 답을 `[1,2,3,4]`로 고정하는 **거짓말**이 있었는데(문제 B), 이제는 **섞으면 정답도 항상 그에 맞게** 바꿉니다. 거짓 라벨이 사라졌어요.

### ② identity_prior = 0.155
"프레임이 **이미 시간순일 확률**"을 학습 중에 **15.5%로 맞췄습니다.** 왜 15.5%냐면, 실제 test 데이터의 no_ordering 비율이 15.5%거든요. 이렇게 하면 모델이 "대략 6~7개 중 1개는 안 섞인 영상이겠구나"를 감으로 익혀서, `[1,2,3,4]`를 적절한 빈도로 답하게 됩니다.

> 참고: 기존 스타일(`mid` 등)과 옛 증강 코드는 **그대로 뒀습니다.** 이전 실험을 재현해야 할 수 있어서, `plain`이라는 새 경로만 추가한 거예요.

## 4. 결과 (실측)

같은 8B 모델에서, **데이터 스타일만** `mid` → `plain`으로 바꿨습니다.

| 지표 | 기존 8B (mid) | **새 8B (plain)** | 변화 |
|---|---|---|---|
| **test LB (실제 점수)** | 0.88132 | **0.90052** | **+1.92pp** 🎉 |
| val EM (내부 검증 점수) | 0.5519 | 0.5782 | +2.6pp |
| em_no_ordering (안 섞인 영상 정확도) | 0.5099 | 0.5629 | **+5.3pp** ← 가설 증명 |
| em_orderable (섞인 영상 정확도) | 0.5599 | 0.5810 | +2.1pp (덤) |

`em_no_ordering`이 크게 오른 게 "no_ordering을 제대로 학습시켰다"는 직접 증거이고, 놀랍게도 **일반 문제(`em_orderable`)까지** 올랐습니다.

> **용어**: `LB`(리더보드)는 대회에 제출해서 나오는 진짜 점수, `val EM`은 우리가 내부적으로 채점하는 연습 점수입니다. `pp`는 퍼센트포인트(0.88→0.90이면 +2pp).

## 7. RunPod에서 삽질했던 것 (다음 사람은 피하세요)

RunPod로 돌리다 만난 함정들. 코드는 이미 고쳐뒀지만 참고하세요:

- **`source cloud/runpod_env.sh` 하면 터미널이 죽음** → 파일이 Windows 줄바꿈(CRLF)이라 그랬음. 고쳐뒀지만, 또 그러면 `sed -i 's/\r$//' cloud/runpod_env.sh` 로 고치거나 환경변수를 직접 export.
- **학습이 너무 느림 (A100인데 37초/스텝)** → 데이터를 나르는 일꾼(worker)이 0명이라 GPU가 이미지 로딩을 하염없이 기다림. `configs/*.yaml`의 `dataloader_num_workers`를 8~16으로.
- **예측이 느림 (42초/스텝)** → 예측은 worker 설정이 안 먹힘. **batch를 키우면**(16→32→64) 빨라짐. A100 80GB면 batch 64도 여유.
- **학습 결과가 엉뚱한 폴더에 저장됨** → `runpod_train`이 설정의 `output_dir`을 무시하던 버그. 고쳐뒀음.
- **Pod를 Stop했다가 다시 켜니 "GPU 사용 불가"** → 멈춘 사이 다른 사람이 그 GPU를 가져간 것. 데이터(볼륨)는 안전하니, 백업만 할 거면 "Start with CPUs"로 켜서 파일 받고 Terminate.

# 🔄 No_ordering 재해석 라운드 (jiyun 브랜치) — 팀원용 요약

> **이번에 뭘 바꿨고 왜 점수가 올랐는지**를 쉽게 정리한 문서입니다.
> 한 줄 요약: **`No_ordering`이 뭔지 우리가 처음부터 오해하고 있었고, 그걸 바로잡았더니 test LB가 0.88132 → 0.90052로 올랐습니다.**

---

## 1. 무엇을 발견했나 (핵심)

데이터에 `No_ordering`이라는 컬럼이 있습니다. 전체의 15.5%가 `True`이고, 그 샘플들의 정답은 전부 `[1, 2, 3, 4]`입니다.

우리는 이걸 **"순서를 정할 수 없는 문제"**(프레임이 애매해서 정렬 불가)라고 이해하고 있었습니다. 그런데 **공식 데이터 설명을 다시 읽어보니 뜻이 완전히 달랐습니다:**

> **"No_ordering: True일 경우 이미지는 셔플링되지 않았으며, 정답은 [1, 2, 3, 4]로 고정됩니다."**

즉 `No_ordering=True`는 **"출제자가 이 샘플은 안 섞었다"**는 뜻입니다. 프레임이 애매한 게 아니라, **원래 시간순 그대로인 정상 영상**이에요. 그래서 답이 `[1,2,3,4]`(= 이미 순서대로)인 거고요.

### 증거 (추측 아니라 데이터로 확인함)

| # | 관측 | 우리 옛 해석("정렬 불가")으로 설명되나? |
|---|---|---|
| 1 | no_ordering 샘플 프레임 3장을 직접 열어보니, 캡션 순서와 **완벽히 시간순 일치** | ❌ 정렬 불가면 이럴 수 없음 |
| 2 | **em_no_ordering(0.596) > em_orderable(0.503)** — 모델이 셔플된 no_ordering 프레임의 원래 순서를 59.6% 복원 | ❌ "정렬 불가"한 걸 정렬한다? 모순 |
| 3 | 검은 프레임·중복 프레임 같은 노이즈가 두 그룹에 **똑같이** 분포 (0.97배) | ❌ no_ordering이 노이즈 덤프였다면 한쪽에 몰려야 함 |

②번이 결정적입니다. **TTA가 no_ordering 샘플도 똑같이 섞어서 물어보는데**, 모델이 원래 순서를 59.6%나 맞힙니다. 정렬이 불가능하면 이게 불가능하죠. **두 그룹은 그냥 같은 난이도의 같은 문제**였습니다.

---

## 2. 그래서 뭐가 버그였나

이 오해 때문에 코드에 **두 가지 문제**가 있었습니다.

### 버그 ① 학습 데이터 15.5%에 거짓 라벨을 가르치고 있었음
증강할 때 no_ordering 샘플의 **프레임은 섞어놓고 정답은 `[1,2,3,4]`로 고정**했습니다. 프레임을 섞었으면 정답도 따라 바뀌어야 하는데, "섞였는데도 답은 그대로"라고 가르친 겁니다. → 모델한테 "이 영상들은 프레임 보지 말고 그냥 `[1,2,3,4]` 뱉어"를 학습시킨 셈.

### 버그 ② 존재하지 않는 개념(UNORDERABLE)을 가르침
프롬프트에서 "순서를 못 정하겠으면 `UNORDERABLE`이라고 답해"라고 시켰는데, 그런 샘플이 **애초에 없으니** 모델이 `UNORDERABLE`을 6,552번 중 **0번** 출력했습니다. 헛수고를 가르친 거죠.

---

## 3. 뭘 바꿨나 — `plain` 스타일

`UNORDERABLE`이라는 개념을 통째로 없애고, **순수하게 "4장을 시간순으로 정렬하는 문제" 하나**로 통일했습니다. 이걸 `plain` 스타일이라고 부릅니다.

핵심 두 가지:
1. **진실 라벨 증강** — no_ordering이든 아니든 구분 없이, 프레임을 섞으면 정답도 **항상 그에 맞게** 바꿉니다 (거짓 라벨 없음).
2. **identity_prior = 0.155** — "프레임이 이미 시간순일 확률"을 test 실제 비율(15.5%)에 맞춰 학습합니다. 모델이 `[1,2,3,4]`라고 답하면 그게 곧 "이미 순서대로" = no_ordering이고, 그대로 제출하면 정답입니다.

> 기존 스타일(`mid` 등)과 옛 증강 함수는 **건드리지 않았습니다.** 이전 체크포인트를 재현해야 할 수 있어서, `plain`이라는 새 경로만 추가했습니다.

---

## 4. 결과 (실측)

같은 8B 모델, **데이터 레시피만** `mid` → `plain`으로 바꿨습니다.

| 지표 | 기존 8B (mid) | **새 8B (plain)** | 변화 |
|---|---|---|---|
| **test LB** | 0.88132 | **0.90052** | **+1.92pp** 🎉 |
| val EM | 0.5519 | 0.5782 | +2.6pp |
| em_no_ordering | 0.5099 | 0.5629 | **+5.3pp** ← 가설 증명 |
| em_orderable | 0.5599 | 0.5810 | +2.1pp (보너스) |

`em_no_ordering`이 크게 오른 게 "no_ordering을 제대로 학습시켰다"는 직접 증거이고, 덤으로 일반 문제(`em_orderable`)까지 올랐습니다.

## 7. RunPod에서 삽질했던 것 (다음 사람은 피하세요)

RunPod로 돌리다 만난 함정들. 코드는 이미 고쳐뒀지만 참고:

- **`source cloud/runpod_env.sh` 하면 터미널이 죽음** → 파일이 Windows 줄바꿈(CRLF)이라 그랬음. 고쳐뒀지만, 또 그러면 `sed -i 's/\r$//' cloud/runpod_env.sh` 하거나 환경변수를 직접 export.
- **학습이 너무 느림 (A100인데 37s/it)** → 데이터 로더 워커가 0이라 GPU가 이미지 로딩을 기다림. `configs/*.yaml`의 `dataloader_num_workers`를 8~16으로.
- **추론이 느림 (42s/it)** → 추론은 워커 설정이 안 먹힘. **batch를 키우면**(16→32→64) 샘플당 시간이 줄어듦. A100 80GB면 batch 64도 여유.
- **학습 결과가 엉뚱한 폴더에 저장됨** → `runpod_train`이 config의 `output_dir`을 무시하던 버그. 고쳐뒀음.
